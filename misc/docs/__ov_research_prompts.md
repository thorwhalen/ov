# `ov` — Research Prompts for Tooling & Method Intelligence

*Author: Thor Whalen*
*Five jobs: four **deep-research** reports (D1–D4) and one **lightweight search-backed brief** (L1). Each prompt is fully standalone — it states its own context, so it can be pasted into a fresh agent with no other files. Each deep report must return Markdown with **Vancouver-style references** ([1], [2], …) and a REFERENCES section with hyperlinks: `[name](url)`.*

**Why only five (and why this split):** deep research costs 30–60 min and many tokens per run, so each job is scoped to a single decision-cluster with explicit comparison axes and a required recommendation/decision-table, to maximize the chance of being right the first time. Run order: **L1 first** (it gates the public API), then D1 → D2 → D3 → D4 in parallel as capacity allows.

## L1 — Responsible-use boundaries & default settings *(lightweight, NOT deep research)*

**Run as a normal search-backed answer (~5–10 min), not a 45-minute deep job.** This is mostly settled knowledge plus a few current cases, and its output is needed *before* the tool's public API and defaults are finalized.

> I am building a tool that, given a URL, drives a web app like a user, captures its DOM/screenshots/network traffic/console, and reverse-engineers the served frontend (JS bundles, source maps, tech stack) to produce UX and architecture reports. It runs against two kinds of targets: the operator's **own** systems (review) and **third-party** systems the operator is authorized to inspect (reconstruction-grade analysis). It is NOT a scraper of user data and must not bypass authentication or access controls.
>
> Give me a concise, current brief on the **legal, ethical, and responsible-use boundaries** of this activity, and turn it into an actionable default-settings checklist. Cover: (1) `robots.txt` and Terms-of-Service implications for automated access; (2) the current US legal landscape on automated access and scraping (e.g. the CFAA after *Van Buren* and *hiQ v. LinkedIn*) and the EU angle (GDPR for incidentally captured personal data, database/sui-generis rights) — keep this practical, not a law-review treatment; (3) reverse-engineering deployed client-side code — what's normal-practice vs. risky; (4) politeness/rate-limiting norms; (5) incidental capture of PII and secrets — what to redact or never store. Then output a **"responsible defaults" checklist** for the tool: an explicit authorization acknowledgement for third-party targets, polite-rate defaults, a no-auth-bypass rule, and redaction-on-by-default for storage (cookies/localStorage/form values). Cite sources with links. This does not need to be exhaustive — I need enough to set sane defaults, not a legal opinion.

## D1 — Capture & operation stack *(deep research)*

**Decision this informs:** the browser-driving + runtime-capture layer, and the design of an autonomous agent that operates the target to produce a meaningful user journey.

> Produce a deep-research report to help me choose and architect the **browser-automation, runtime-capture, and autonomous-operation layer** for a Python system that drives arbitrary web apps and records their complete behavioral and network behavior, then analyzes them.
>
> **Part A — Capture stack.** Compare **Playwright (Python)** as the baseline against **Puppeteer**, **Selenium / WebDriver BiDi**, and **raw Chrome DevTools Protocol (CDP)**. I have a strong prior toward Playwright Python; your job is to confirm or challenge it and to map exactly *where it needs CDP supplementation*. For each candidate, address concretely: (1) capturing the full network stream — requests, responses, **response bodies** (and their content-type/size limits), timings, initiator chains — and the fidelity and limits of **HAR export**; (2) **WebSocket and SSE** frame capture; (3) console/error/page-exception capture; (4) extracting the full **accessibility tree** (the CDP `Accessibility.getFullAXTree` route and what the high-level APIs omit); (5) reading **cookies / localStorage / sessionStorage / IndexedDB**; (6) tracing/perf hooks. Then state clearly **what requires a proxy layer** (mitmproxy / Playwright's built-in record / browsermob) to obtain — e.g. response bodies the high-level API won't surface, or TLS-level detail — and when that complexity is worth adding. Give concrete code patterns for **attaching a CDP session from Playwright Python**. Briefly cover anti-bot/fingerprint-evasion stacks (stealth plugins, Camoufox, undetected variants) **and their ethical limits** — note them as an optional, off-by-default capability, do not center the report on evasion.
>
> **Part B — The operation loop (host-agent-orchestrated).** My system is consumed primarily by a **host agent (Claude Code)** that orchestrates a library of tools via skills — the manager/control loop lives in the host, not in my package, and I will only later optionally productize it into a self-contained Python agent. So research the operation loop as **(a) the tool primitives my package must expose** and **(b) the policy a host agent needs to drive them**, not as a bespoke agent framework to build now. Survey how LLM host agents **operate web apps**: **vision-grounded** (screenshot + coordinates), **accessibility-tree / DOM-grounded** (set-of-marks, element-role targeting), and hybrid approaches. Reference the relevant systems and benchmarks (e.g. **WebArena, WebVoyager, Mind2Web, SeeAct, browser-use, Playwright-MCP**, and computer-use agents) for grounding-accuracy, reliability, and cost trade-offs — and note specifically how **Playwright-MCP / browser-use** expose browser control to a host agent as tools, since that is close to my target shape. Address how the host **perceives affordances**, decides the next action toward a goal, **recovers from errors**, **detects no-progress / loops**, and stays bounded (max-steps/time) — and which of these belong in the tool layer (deterministic, e.g. affordance extraction, action execution, loop/progress detection helpers) vs. the skill/policy layer (host judgment). Distinguish three operating strategies I support — **crawl-and-map**, **goal-pursuit**, **guided-replay** — and how each should **log per-step intent** so the journey trace is itself usable as UX evidence. Briefly note what the eventual lift to a self-contained in-package agent would add on top.
>
> **Deliverables:** (i) a recommended **layered capture architecture** (what Playwright handles, where CDP attaches, when a proxy is justified) with a **decision table**; (ii) a recommended **operation design split into a tool layer** (the deterministic primitives my package exposes: affordance extraction, action execution, journey/intent logging, loop & no-progress detection) **and a host-agent policy layer** (what a Claude Code skill should instruct — strategy switching, recovery, bounding), plus a note on what an optional later in-package agent would add; (iii) concrete Python code patterns for the non-obvious parts (CDP attach, WS capture, HAR + body capture). Markdown, Vancouver references, hyperlinked REFERENCES section.

## D2 — Architecture inference from served artifacts *(deep research)*

**Decision this informs:** how `ov` reconstructs the target's frontend stack and API surface from what it can observe and download — fingerprinting, source-map recovery, and API synthesis.

> Produce a deep-research report on **inferring a web app's frontend architecture and API surface from externally observable artifacts** (served HTML/JS/CSS, response headers, runtime globals, and captured network traffic). This is for a Python tool whose goal is reconstruction-grade intelligence: enough to rebuild a comparable system, or to audit one's own.
>
> **Part A — Tech & dependency fingerprinting.** Evaluate maintained open fingerprint databases — **Wappalyzer / the community `webappanalyzer` fork** (ruleset structure, licensing, how to run it programmatically against headers+DOM+globals+script-URLs) — and complements: **Retire.js** (vulnerable-library detection), and what builtwith/whatruns-style services add. Detail the signal sources and their reliability: response headers, script/CDN URLs, DOM markers, `window` globals (`__NEXT_DATA__`, `__NUXT__`, `__remixContext`, devtools hooks), in-bundle comments, and **`node_modules/` paths leaked in source maps** for version recovery. Explain how to infer the **bundler** (webpack/Vite/Turbopack/esbuild/Rollup) and the **rendering model** (CSR / SSR / SSG / streaming-SSR) from served artifacts. Address false-positive rates and how to attach **confidence scores**.
>
> **Part B — Bundle & source-map reverse-engineering.** Cover **source-map consumption** (the `source-map` library and current `sourcemap`/`sourcemap-cli` tooling) to un-minify and reconstruct the original **module/file tree and component boundaries**; precisely what is recoverable when maps are present vs. absent; tools to **beautify / de-obfuscate** sourceless bundles; recovering in-bundle data safely (route tables, API base URLs, feature flags, embedded config). Because the mature tooling here is JavaScript, recommend a clean **Python-orchestrated Node-sidecar** pattern with sane process boundaries.
>
> **Part C — API-surface synthesis from traffic.** Cover converting captured **HAR → OpenAPI** (tools such as **har2openapi, mitmproxy2swagger, Optic**) and inferring request/response **JSON Schemas** from observed examples; detecting and introspecting **GraphQL** (introspection when enabled, schema inference from observed operations when disabled); distinguishing **REST vs RPC vs GraphQL**; recovering **auth schemes** (bearer/cookie/OAuth) from headers; detecting **realtime layers** (WebSocket/SSE) and their message shapes; and **merging multiple journey runs** into one coherent API surface with coverage/confidence scoring.
>
> **Deliverables:** a recommended **three-stage inference pipeline** (fingerprint → bundle recovery → API synthesis) with the specific tools/libraries to use at each stage, a **decision table** of detectors → signal sources → confidence, and the recommended Python↔Node sidecar boundary. Note legal/ethical limits of reverse-engineering deployed JS briefly (don't dwell). Markdown, Vancouver references, hyperlinked REFERENCES section.

## D3 — Automated UX & accessibility evaluation *(deep research)*

**Decision this informs:** the UX-analysis lens — which signals to compute deterministically, how they become severity-ranked findings, and where LLM judgment adds value.

> Produce a deep-research report on **automated and semi-automated evaluation of web UX and accessibility**, suitable for programmatic application to a live web app that has been driven through user journeys by an automated agent (so I have: screenshots per state, a step-by-step journey trace with the agent's stated intent per step, full DOM + accessibility tree, console errors, and performance timings).
>
> **Part A — UX evaluation.** Map classic **heuristic-evaluation frameworks** (Nielsen's 10 heuristics; cognitive walkthrough) onto *machine-observable signals* — for each heuristic, state what in my captured data could evidence a violation. Cover **quantitative UX metrics** derivable from an automated journey trace: task success, time-on-task, error rate, **steps-to-goal**, **backtracking / dead-ends**, form friction (field count vs. completion). Cover **performance-as-UX** via **Core Web Vitals** (LCP / INP / CLS / TTFB / FCP) and crucially **how to attribute each metric to a specific journey step** rather than the page as a whole. Cover **information-architecture / navigation-graph** analysis (depth, breadth, labeling consistency, orientation cues) and **microcopy / empty-state / error-state** evaluation (including how to deliberately drive the app into those states). Survey the state of the art in **ML/LLM-based usability evaluation** — vision models reasoning over annotated screenshots, agentic usability testing — and where it's reliable vs. where it hallucinates.
>
> **Part B — Accessibility auditing.** Compare engines: **axe-core (Deque)**, **Lighthouse a11y**, **Pa11y**, **IBM Equal Access**, **WAVE**. Cover their coverage against **WCAG 2.1/2.2 AA**, the well-known **~30–40% automatable ceiling** (what *cannot* be detected automatically), how to run **axe-core injected via the browser per app state**, mapping violations to WCAG criteria, **keyboard-navigation and focus-order** evaluation via the accessibility tree, **color-contrast** computation, and **ARIA-live / dynamic-content** checks.
>
> **Deliverables:** (i) a **signal catalog** — a table of UX/a11y signals, each with its data source, how to compute it, and how to assign **severity** (e.g. severity × reach); (ii) a recommended **deterministic-first pipeline** that computes findings without an LLM, plus a clearly delimited **LLM layer** that adds narrative judgment over an evidence bundle (annotated screenshots + the findings) — including how to keep the LLM grounded and avoid invented findings; (iii) a recommended **finding schema** (signal, severity, evidence-ids, location, suggested-fix). Markdown, Vancouver references, hyperlinked REFERENCES section.

## D4 — Grounded LLM analysis, host-agent orchestration & synthesis *(deep research)*

**Decision this informs:** how analysis judgment is produced — primarily by a **host agent (Claude Code) following skills** that orchestrate my deterministic tools — and how many reports compress into one agent-consumable synopsis. Note: my system's near-term manager is the host agent, not an in-package agent; building a self-contained in-package multi-agent system is an optional *later* step. Research accordingly.

> Produce a deep-research report on **grounding LLM analysis in captured web-application evidence to produce reliable, low-hallucination UX and software-architecture reports**, and on **how to orchestrate this work via a host agent (Claude Code) driven by skills**, with in-package agents treated as an optional later productization. Assume the upstream system has already captured: annotated screenshots (bounding boxes marking the element each journey step targeted, captioned with the step's intent), a journey trace, network/API facts, detected tech-stack facts, and accessibility/performance metrics.
>
> **Cover:** (1) **Evidence-bundle assembly** for multimodal models — how to package annotated screenshots + structured facts so a vision-capable LLM reasons over grounded inputs rather than guessing; what to include vs. omit to control token cost. (2) **Hallucination-reduction techniques** specific to this setting — cite-the-evidence prompting, **structured outputs via JSON-schema / tool-use / Pydantic-validated** returns, and a hard separation between *deterministic facts* (computed upstream) and *LLM judgment* (so the model interprets but does not invent facts). (3) **Prompt-and-task patterns** for the two analytical jobs: **architecture reconstruction** ("from these stack/bundle/API facts, infer the architecture and produce a rebuild blueprint") and **UX critique** ("from these findings and screenshots, produce severity-ranked issues with concrete fixes"); include how each should differ for **reconstruction mode** (foreign target — infer design intent, produce a reusable interaction-pattern catalog) vs **review mode** (own system — critique + concrete fixes, and diff against a prior run if present). (4) **Orchestration: host-agent-via-skills vs. in-package agents.** Research the emerging **"the harness is the agent"** pattern — giving a capable host agent (Claude Code) a set of well-scoped tools plus a thin **skill** layer (procedural knowledge), and letting the host supply planning/delegation/recovery — versus building a bespoke in-package multi-agent orchestrator. Cover: how to author skills (e.g. Anthropic Agent Skills / `SKILL.md` conventions, MCP tool exposure) so a host reliably orchestrates a tool library; the trade-offs (speed-to-working-system, cost, determinism/repeatability, testability) of host-orchestration vs. a self-contained agent; how to keep the deterministic core callable with **no model** so the system stays testable and cheap; the **conceptual role split** (Operator / UX-Analyst / Arch-Analyst) expressed first as *skills the host follows* and later as *thin in-package agents sequencing the same tool functions*; and the **mechanical lift path** from a working tool+skill set to a productized agent system (what changes, what's reused). (5) **Extract-and-aggregate / synopsis** patterns — how to compress many per-section reports into a single dense, machine-readable synopsis (structured findings, not prose) that a *downstream creation/modification agent* can consume to build or change a related system.
>
> **Deliverables:** (i) a recommended **evidence-bundle spec** and **structured-output schema** approach; (ii) recommended **prompt/task designs** for the Arch-Analyst and UX-Analyst in both modes; (iii) a recommended **orchestration design**: the skill set a host agent (Claude Code) needs to drive the tool library (which skills, what each instructs, how they compose), with a clear statement of what stays deterministic/model-free, plus the **mechanical lift path** to optional in-package agents; (iv) a recommended **synopsis format** (human-readable Markdown + machine-readable JSON) for downstream agents. Markdown, Vancouver references, hyperlinked REFERENCES section.
